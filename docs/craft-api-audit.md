# Крафт: состояние бэкенда и фронтенда

Проверено 10 сентября 2026 по локальному backend `master`, commit `63855e2`.
Это аудит исходников, а не проверка доступности production.

## Маршруты

| Маршрут | Что есть в master | Пригодность для SPA |
| --- | --- | --- |
| `/v1/items`, `/v1/items/{id}` | Стандартные REST-правила Yii в `yii2/common/modules/craft/config/urlRules.php` | Нет `api/modules/v1/controllers/ItemsController.php` |
| `/v1/recipes`, `/v1/recipes/{id}` | Стандартные REST-правила Yii | Нет `RecipesController.php` |
| `/v1/inventory`, `/v1/inventory/{id}` | Стандартные REST-правила Yii | Нет `InventoryController.php` в API v1 |
| `/craft/category/index`, `/craft/item/index`, `/craft/recipe/index`, `/craft/inventory/index`, `/craft/history/index` | Контроллеры общего модуля наследуют `yii\web\Controller`, рендерят серверные представления | Не JSON API |
| `/craft/inventory/craft` | `actionCraft()` выбирает рецепт с ID 3, выполняет сервис и возвращает redirect | Не принимает ID выбранного рецепта; не подходит для SPA |
| `/craft/inventory/add-item` | `actionAddItem()` выбирает предмет с ID 5 и количество −2, затем redirect | Служебное действие с фиксированными значениями, не магазин |
| `/v1/craft-item`, `/v1/craft-recipe`, `/v1/craft-inventory/my`, `/v1/craft-recipe/{id}/craft`, `/v1/craft-shop`, `/v1/craft-shop/{id}/buy` | Использовались прежним фронтом, в бэкенде отсутствуют | Вызовы удалены из адаптера |

Модуль craft подключён через common/config и bootstrap API. Это регистрирует правила URL, но не создаёт отсутствующие контроллеры v1. В `api/modules/v1/Module.php` нет переназначения этих контроллеров.

## Данные

Модели существуют, но сериализация ответа SPA не реализована:

- `CraftItem`: `id`, `name`, `description`, `crafting_time`, числовой `rare`, `category_id`, `active`. Нет подтверждённых `code`, `icon`, `price_credits` и строковой `rarity` старого мока.
- `CraftRecipe`: `item_id` результата, `category_id`, `active`; связи `item`, `recipeItems`, `recipeTools`. Нельзя считать, что API отдаёт `output`, `ingredients`, `cost_credits`.
- `CraftInventory`: `user_id`, `item_id`, `item_quantity`, `slot`; пустой слот допускает `item_id = null`. Один предмет может занимать несколько слотов. Старое `{item, qty}` не является серверным контрактом.
- `CraftService::craftItem(Person, CraftRecipe): void` выполняет цепочку middleware. Сам сервис не задаёт публичный HTTP-контракт.

## Изменения фронта

- Страница `/craft` показывает состояние недоступности крафта аккаунта и вход в существующую локальную мастерскую.
- `/exchange/shop` объясняет недоступность магазина аккаунта и ведёт в `/craft?mode=workshop`.
- Адаптер `src/services/api/craft.ts` отклоняет операции с `CRAFT_UNAVAILABLE`, не отправляя запросы на выдуманные маршруты. Старый mock-флаг не подменяет операции аккаунта.
- Убрано списание и возврат кредитов через auth-store для покупок моковых материалов.
- Мастерская продолжает использовать отдельный баланс и localStorage. Это демо, не серверный инвентарь.

## Что требуется для полноценного подключения

Реализовать REST-контроллеры чтения с авторизацией и фильтрацией инвентаря по текущему пользователю, определить JSON-сериализацию предметов, рецептов (включая ресурсы и инструменты), слотов и пагинации. Добавить POST-команду крафта с ID рецепта, проверкой доступности, атомарным изменением ресурсов, защитой от повторов и согласованным ответом результата/ошибок. Магазину нужен отдельный подтверждённый контракт цен и покупки с серверным списанием баланса.

После этого заменить недоступный адаптер реальным, валидировать JSON и адаптировать DTO к UI. Простого переименования URL или переключения env недостаточно. Разработка этих серверных операций в текущую правку фронта не включена.
