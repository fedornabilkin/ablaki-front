# Общие списки и функции сообщества

Цель: выполнить пользовательский запрос на серверные списки, URL-состояние, хедер, статистику и игровые/форумные возможности. Разработка непосредственно в master frontend и backend, работа четырьмя потоками с разделённым владением файлами.

## Группа A: Основа
- [x] A1. Перейти в master, сохранить готовую историю и удалить влитую рабочую ветку frontend.
- [x] A2. Закрепить master и единый контракт списков в соглашениях.
- [x] A3. Общие фильтры, серверный поиск с debounce, URL и метаданные пагинации.

## Группа B: Страницы
- [x] B1. Прилипающий хедер со сжатием, счета, ежедневные награды и онлайн.
- [x] B2. Статистика, рефералы, типы истории и единые списки.
- [x] B3. Игровой кон, recent, today и собственные игры.
- [x] B4. Передача 1 Cr сообщению и список передавших с транзакциями backend.
- [x] B5. Случайная подсказка из API внизу страниц.

## Группа C: Проверка и публикация
- [x] C1. Общие тесты frontend и backend на изолированных данных.
- [x] C2. Проверить в браузере URL/back-forward, мобильную компоновку и взаимодействие блоков.
- [x] C3. Сохранить проверенный код frontend и backend коммитами в master.
- [x] C4. Отправить backend master в GitHub — c875c7c, реализация API в 959b8af.
- [ ] C5. Подготовить зависимости и обе миграции, обновить API; требуется расположение и способ обновления действующего backend.
- [ ] C6. После готовности API отправить frontend master и проверить автоматический деплой.

Критерий готовности: общий UI подключён ко всем доступным спискам, API фильтрует до подсчёта/пагинации, суммы и онлайн не выдумываются; production-операции не выполняются в тестах. Миграции и PostgreSQL/MySQL concurrency требуют отдельной проверки целевого окружения.

Результаты локальной проверки: [отчёт](../docs/lists-and-community-verification.md). Публикация frontend зависит от обновления API: push master запускает production deploy автоматически.
